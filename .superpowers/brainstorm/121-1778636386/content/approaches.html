三种架构方案

将所有新需求（三层信息、武器/敌人库、注入模块、动态生成）融入现有系统

A

增量扩展 — 扩展现有 parser/pipeline

在现有 JSON 模板上新增 L1/L2/L3 标记字段和新的 side_effect 类型（SpawnEnemy, GrantItem）。武器/敌人库作为新 data 目录。注入模块作为 pipeline 新阶段。利用已有的 improvise_prompt + suggested_flags 路径实现 LLM 自主生成。

优势

  • 最大化复用现有代码，改造成本最低
  • 与已有 side_effects、RequirementResolver、pipeline 阶段无缝对接
  • improvise_prompt 已经是"偏离轨道"的钩子
  • 开发周期最短

劣势

  • 现有 JSON 结构可能越来越冗长
  • 三层信息标记和原有字段混在一起
  • 未来大规模重构可能困难
B

新子系统 — 独立的模块设计工具包

创建 src/module_designer/ 包（parser、library manager、injector 各自独立）。三层信息用新的文档格式（markdown + frontmatter）。库文件有独立的版本管理。game_loop 新增 RuntimeInjection 阶段。

优势

  • 边界清晰，各模块可独立测试
  • 库版本管理更规范
  • 不影响现有 game_loop 稳定性

劣势

  • 与现有系统并行，有两套格式的维护成本
  • parser 的逻辑在 parsers.py 和 module_designer 之间会有重叠
  • 开发周期长
C

混合方案 — 渐进式重构

第一步按方案A快速落地（扩展 JSON + pipeline），第二步将成熟模块提取为独立子系统。三层信息先在 JSON 中用字段标记，后续可迁移到独立文档。库系统从一开始就独立设计。

优势

  • 先出可用成果，再优化架构
  • 降低单次改动风险
  • 方向清晰，不会走入死胡同

劣势

  • 需要两次修改（先扩展后提取）
  • 中间的 JSON 格式可能不完美
