# 剩余 ISSUES 整体工作计划(2.5 步)设计

> 2026-08-26 与用户讨论拍板。宏观设计,刻意不含实现细节;每个阶段开工前再出对应执行方案(writing-plans)。
> 范围来源:docs/ISSUES.md 活跃区(F 系缺口 + B 系 bug + R 系重构)。

## 0. 背景与目标

阶段 0 bug 批已收口,ISSUES 活跃区剩余:功能缺口 F1–F35(CLI 域)、B1 存读档、R1–R3 重构。
目标:用一个三阶段结构把剩余工作排掉——先清快修项,再做必要的核心架构调整,最后按簇滚动完成功能升级。

## 1. 已确认的边界决策

| 决策点 | 结论 |
|--------|------|
| 前端域(F36–F43、B19) | 不纳入本计划,维持"前端不排期除非阻塞 CLI"约定 |
| 计划骨架 | 方案三:R1 拆分先行,数据模型改造不设独立大段,随各功能簇开工时按真实需求调整 |
| 重构范围 | 核心是 process_turn 拆分(R1);其余架构调整由剩余功能的实际需求驱动 |
| 功能覆盖 | 六簇尽量覆盖,但逐点评估做/缓/非目标,不保证每个需求点都做 |
| B1 存读档 | **推翻"排最后"旧约定**,提前并与 F14/E 簇/R1 统一规划(均为数据模型+存档格式,一次设计避免多次迁移) |
| F9 去重方案 | 简单 seen 集合入档(`san_seen_sources: set[str]`);不预留大系统,E 簇记忆系统落地时迁移成本近零 |
| F16 方案 | **降级为"测试锁定 + 文档配方",不做新机制**:infra 已能表达锁-钥匙(`item:具体名` 硬条件 + 锁 interaction entity 检定成功 `mark_completed` → 门 `flag:` 即时通过);"锁匠"技能与"开锁工具"物品已在库,缺的是实际使用样例 |

## 2. 三阶段结构

```
Step1 快修批(行为小改,无结构依赖)
  → Step2 架构段(R1 拆分 + 簇评估文档)
  → Step3 功能升级(六簇滚动,每簇先评估后实现)
```

### Step1 快修批(4 项,按此顺序)

| 序 | 项 | 说明 |
|---|---|------|
| 1 | F11 库 schema 作者参考文档 | 纯文档,零风险;含"锁-钥匙模式"配方(为 F16 铺垫);作为后续库字段改动基线 |
| 2 | F4 timed 边界测试补齐 | 纯测试,零产品代码 |
| 3 | F9 SAN 遭遇去重 | `san_seen_sources` 集合入档,全局首次目睹才 check;multi_attack 叠加一并处理 |
| 4 | F16 锁-钥匙测试锁定 | 最小锁实体 fixture 跑通"开锁工具检定成功 → 门 flag 通过"端到端链路并锁测试;不新增机制、不动真实模组 |

### Step2 架构段(统一设计:R1 + B1 + F14 + E 簇数据模型)

1. **统一数据模型与存档设计**:B1 存读档三连(from_dict 吞异常/读档引用不一致/`_npc_injected_at_ids` 入档)+ F14 技能 checked 标记 + E 簇(F22 线索实体/F25 narrator 记忆)的入档结构,一次设计到位,存档格式只迁移一轮。
2. **R1 纯结构拆分**:keeper.py(~1700 行)/combat.py/scenario_core.py 拆分,行为不变。验收:拆分前后默认套件全绿。
3. **《簇→架构需求评估文档》**:对六簇逐点评估,每点标注 **做/缓/非目标** + 所需数据模型改动 + 簇内排序。本文档决定 Step3 每簇范围,用户逐簇确认后才开工。

### Step3 功能升级(六簇滚动)

| 簇 | 内容 | 排序 |
|----|------|------|
| A. COC 核心规则 | F5 疯狂 / F6 重伤濒死 / F7 战斗反应 / F8 恢复+mythos | **默认最先**(规则核心、模组高频) |
| B. 世界物品交互 | F1 / F15 / F17 / F21 / F23 | 由 Step2 评估文档定 |
| C. NPC 系统 | F26 / F27 / F28 / F29 / F20 | 同上 |
| D. 时间与环境 | F18 / F19 / F10 | 同上 |
| E. 叙事与成长 | F22 / F25(数据模型部分已提前到 Step2 统一设计,Step3 做消费侧) | 同上 |
| F. 模组工具链 | F31 / F32 / F33 / F34 / F35 | 同上 |

每簇开工流程:评估文档确认该簇范围 → 需要的数据模型调整先落 → TDD 实现 → 收口回归。每簇收口后保持可玩状态。

## 3. 流程约定(全阶段适用)

- main 分支直接推进;TDD;收口 `pytest tests/ -q`
- 改 prompt/parse/narrator 主路径时跑 `pytest -m real_llm_smoke`;全量 real_llm 仅用户明确要求
- 每项收口同步 MAINTENANCE.md(函数/行号/调用关系)与 docs/ISSUES.md(活跃→已收口)
- 不提交无关脏文件(autosave、supplements、imp.py、test.py、.claude/)
