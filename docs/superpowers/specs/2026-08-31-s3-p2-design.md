## 1. F5 疯狂体系（轻方案）

### 1.1 设计逻辑

不改 SAN 损失的三个出口内部算法，在出口处统一汇入钩子 `ScenarioWorld.on_san_loss(loss, source)`：

```
出口① 探索 markup @stat_change(SAN,-N) → apply_stat_change (models.py:404)
出口② 战斗遭遇 _san_check_and_lose (combat.py:147)          ──> on_san_loss(loss, source)
出口③ 施法 cost.san 直扣 (judge.py:122 / combat.py:930) ─────╯      │
        ├─ 累计 san_lost_today（入档；advance_time 跨日清零，
        │   参照 san_seen_sources 入档集合模式 scenario_core.py:702）
        ├─ 单次 loss ≥ 5 → INT 检定 → 失败置 temporary_insanity
        └─ 当日累计 ≥ 初始SAN/5 → 置 indefinite_insanity
                     │
player.insanity 非空 → build_snapshot 携带 → keeper/narrator prompt 注入演绎
                     → 骰子/技能检定提示词联动说明（改 prompt → real_llm_smoke）
```

### 1.2 数据模型（入档）

`player.insanity: dict`，默认空：

```json
{
  "temporary": "",       // 临时疯狂自由文本（LLM 现场生成）
  "indefinite": "",      // 总结性疯狂自由文本
  "phobia": "",          // 恐惧症标记（自由文本）
  "mania": "",           // 躁狂症标记（自由文本）
  "san_lost_today": 0,
  "san_day": 1           // 计数所属游戏日，跨日由 advance_time 清零
}
```

存档 to_dict/from_dict 增量兼容（缺省=无疯狂，E 簇既有模式）。

### 1.3 判定规则（COC7）

- 单次损失 ≥5 → INT 检定（走 `check_skill` 属性路径）：失败 → 临时疯狂。
- 当日累计损失 ≥ **初始 SAN 的 1/5**（建卡 SAN，非当前值）→ 总结性疯狂。
- **施法 SAN 消耗计入累计**（拍板：COC7 任何 SAN 损失均累计）。
- 临时疯狂持续时长不做机械结算（轻方案：LLM 演绎，文本留存到 keeper/玩家叙事中自然解除）。

### 1.4 表现层

- 疯狂文本 **LLM 现场生成**（拍板）：触发时一次 flash 调用，输入=触发事件上下文+角色简况，输出 ≤100 字自由文本写回字段。
- `build_snapshot` 非空时携带 insanity 段；`build_keeper_prompt`/`build_narrator_prompt` 注入【疯狂状态】，指令「演绎其影响，不机械复述」。
- 骰子/技能检定提示词补充疯狂相关说明（联动项，评估 §8-2）。
- 行为控制（强制行动/失控回合）**不做**（轻方案边界）。

### 1.5 上下游标记

| 侧 | 更改 | 状态 |
|---|---|---|
| 【运行时】 | `on_san_loss` 钩子 + 三出口接线；`insanity` 字段入档；snapshot/keeper/narrator/检定 prompt 注入 | 本批实现 |
| 【生成端】 | 模组 san_loss 标注与疯狂触发频率的关系说明；生成器可在高 SAN 事件预写疯狂文本提示 | **暂无生产端** → §10 清单 |

## 2. F23 实体可重复策略

### 2.1 设计逻辑

现状硬挡单点：judge.py:271-276 `_is_entity_completed` → 一刀切拒绝。

- L2 schema `Entity` 增 `repeatable: bool = false`（拍板：两档 once/repeatable，默认 once 保持现状；diminishing 缓）。
- `_execute_entity` 门前判断：completed 且非 repeatable → 挡（现状）；completed 且 repeatable → 放行重跑结算。
- `mark_completed` 照常写 runtime_state（幂等；`flag:`/`item:` 硬条件不受影响，judge.py:523-541）。
- prompt 呈现同步：repeatable 实体完成后**不进已完成隐藏段**（prompts.py:356-370），继续可见可再触发。

### 2.2 上下游标记

| 侧 | 更改 | 状态 |
|---|---|---|
| 【运行时】 | `Entity.repeatable` 字段；judge 门前判断放开；prompt 已完成段呈现规则 | 本批实现 |
| 【生成端】 | L2 schema/生成器产出默认 once；「重读文件/复查现场」类标 repeatable | **暂无生产端** → §10 清单 |
| 下游消费 | F32 实体触发率不受 repeatable 影响（completed 语义不变） | 无需改动 |

## 3. F18 时刻事件触发（降级版）

### 3.1 设计逻辑

降级版（已拍板）：玩家不动时间不走，不做 idle 推进；`advance_time` 跨越时刻点即触发。

- `world.scheduled_events: list[dict]` 入档：`[{id, at_minutes, markup, description, fired?}]`
  - `at_minutes` = clock.game_time 绝对时刻。
  - **payload 载体=markup 文本**（拍板）：触发时 `parse_markup_all` + `apply_side_effects` 结算，零新执行器，可表达生成敌人/改 flag/给物品/属性变更。
  - 触发后出队（一次性）。
- 检测挂在 `advance_time`（scenario_core.py:755-769 时间钩子区）：
  `old_time < at <= new_time` → 触发。与 F8 跨日检测同位。

### 3.2 上下游标记

| 侧 | 更改 | 状态 |
|---|---|---|
| 【运行时】 | `scheduled_events` 队列入档；`advance_time` 跨越检测 + markup 触发 | 本批实现 |
| 【生成端】 | 生成器声明「22:00 凶手行动」类时刻事件；L2 声明格式（markup payload） | **暂无生产端** → §10 清单 |
| 下游消费 | 触发 markup 与 keeper markup 同管道，SAN 损失自动汇入 F5 钩子 | 随 F5 生效 |

## 4. F10 周期性/环境效应

### 4.1 设计逻辑

`timed_effects` 条目扩展（models.py:201）：

```json
{
  "id": "毒发", "description": "...", "expire_at": 1234,
  "interval": "round|hour|day",       // 缺省=纯计时（现状行为）
  "payload": [ {effect 原子}, ... ]   // heal/mp_change/markup/timed 子集
}
```

- `interval: hour|day` → `_tick_time_effects`（scenario_core.py:773-801）按本次 `advance_time` 跨越的 interval 次数结算 payload。
- `interval: round` → combat `_tick_temporary_effects`（combat.py:1246-1255）轮末结算。
- payload 原子复用 8 原子体系；探索侧结算逻辑参照 judge.py:193-252 executor，战斗侧参照 combat.py:954-1024，双侧同步扩（不抽共享 executor，两侧各自小循环，与现状一致）。
- 到期清除行为不变。

### 4.2 上下游标记

| 侧 | 更改 | 状态 |
|---|---|---|
| 【运行时】 | timed 条目扩 `interval`+`payload`；`_tick_time_effects`/`_tick_temporary_effects` 双侧结算 | 本批实现 |
| 【生成端】 | 生成器可写「毒每轮掉 HP / 雾中每轮 SAN / 诅咒每日发作」类周期效应原子 | **暂无生产端** → §10 清单 |
| 下游消费 | SAN 类 payload 汇入 F5 钩子；与 F8 恢复对称（恢复=config 集中参数，周期伤害=模组数据） | 随 F5 生效 |

## 5. F31 模组体检 lint（展开）

**干什么**：模组的静态体检——生成完/手写完跑一条命令，像编译器报错一样输出分级报告，回答「这个模组结构对不对」。

新建 `src/module_designer/lint.py` + `src/module_designer/__main__.py`：

```
python -m module_designer.lint <模组目录>
```

输出示例：

```
验证完成：2 错误, 3 警告, 1 信息
  [error] L2.scene[书房].entity[密道开关].requires → 引用不存在的 flag「det_study_unlocked」
  [error] entity id「信封」在场景 书房/阁楼 重复定义
  [warn]  场景「地下室」从起点不可达（依赖图 BFS）
  [warn]  场景「码头仓库」无任何入口指向（孤立场景）
  [info]  检定难度分布：30-40档×2 / 50-60档×8 / 70+档×11 ← 偏难
```

复用 `validate_l1/l2/l3` + `cross_validate_layers` + `SchemaReport`（error/warning 分级现成，layered_schema.py:194-264）。新增 5 类检查：

| 检查 | 级别 | 说明 |
|---|---|---|
| entity id 跨场景唯一性 | error | 现无 |
| 引用存在性扩编 | error | cross_validate 现 5 类（layered_pipeline.py:97-219）→ 补 markup 内引用、npc_profiles、结局引用 |
| 场景/实体可达性 | warning | DependencyGraph 加 BFS（现只有 detect_cycles，dependency_graph.py:70-100），报起点不可达 |
| 孤立场景 | warning | 无任何入口指向 |
| 检定难度分布 | info | check 值分布直方，供难度标定参考 |

exit code = 是否有 error，供生成管线门禁用。与游戏代码零耦合。

**上下游标记**：【运行时】无改动（纯工具层）；【生成端】lint 本身就是管线工具——本批交付 CLI，「接入生成管线出货门禁」属管线侧集成，**暂无生产端** → §10 清单。

## 6. F32 试玩报告 / 难度标定（展开）

**干什么**：模组的动态体检——llm_player 自动跑一遍模组，从日志聚合成报告，回答「这个模组玩起来顺不顺」。与 F31 互证：F31 说可达但 F32 从未到达 → 多半是线索链引导问题而非结构问题。

新建 `src/module_designer/playtest_report.py`，输入=llm_player 产物（`_summary.json` 全量 turns_detail + mech 行，llm_player.py:138-222），输出=单次试玩报告（markdown + json）：

输出示例：

```
# 《古宅钟声》试玩报告
场景覆盖率：18/30（60%）          ← 12 个场景是死内容
结局触达：ending_escape（T47）；ending_truth 未触达 ← 条件可能太苛刻
实体触发率：41/58；未触发关键实体：「暗格钥匙」「阁楼日记」
检定分布：成功率<40% 的检定集中在 图书馆×3（check 75/80/85）← 过难定位
```

指标与数据来源：

| 指标 | 数据来源 |
|---|---|
| 场景覆盖率（到达/总数） | turns_detail location 序列去重 |
| 结局触达（ending id + 回合数） | mech 行 ending 字段 |
| 实体触发率 + 未触发清单 | completed entities / 总数（与 F31 可达性互证） |
| 检定难度分布（check 值 × 成败 交叉表） | mech 行 entity/tier/check 字段 |

单次报告先行（拍板）；多次试玩汇总等 F34 一起。
